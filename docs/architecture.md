# 经营应用架构与核定规则

本应用把“金额归属的确定性核定”与“净增收益的统计推断”严格分离：
前者按合同条款逐分计算、可复算、可对账；后者只在可识别人群内给出点估计与
区间，保留不可认定的部分。统计区间不会推迟任何一笔有明确条款的费用核对。

## 模块结构

| 模块 | 职责 |
| --- | --- |
| `app/money.py` | 整数金额分摊：按正权重分摊、余分按字典序、按件拆分；全程整数，无浮点金额 |
| `app/models.py` | 追加式事实仓库 `FactStore`：资料包只增不改，`revises` 保留更正链，提供 as-of 视图 |
| `app/basket_engine.py` | 篮子核定引擎：顺序分摊、门槛失效、退货冲回、待追收、四类归属与守恒校验 |
| `app/funding.py` | 费用确认台账：已确认金额不被无声替换、确认差额挂账、争议按范围冻结 |
| `app/analysis.py` | 净增收益识别：可比人群界定、分层近邻匹配、自助法区间、不可识别部分单列 |
| `app/planning.py` | 方案与预算：历史支持范围、争议预留、独立/合并可行性与实际缺口 |
| `app/repository.py` | 版本化状态与全链路溯源：每次核定存版本，可 diff，可追到原事实与合同 |
| `app/cli.py` / `run.py` | 统一命令行入口（`python -I run.py ...`） |

## 事实与时间

* 每条事实记录来源包、`known_at`（可获知时间）与原始负载；`occurred_at` /
  `effective_at` 是实际发生时间，两类时间不互换。
* 历史分析只用 `known_at <= 截点` 的资料；`returns` 同 line_id 取最新累计
  快照，绝不相加；`claims` 折叠更正链后取最新状态，`pending` 不改事实，
  `accepted` 只替换其 `target` 字段。
* 原始资料包永不改写，平台的逐项决定输出为独立记录，后续更正以新资料包进入。

## 篮子核定规则

### 购买时点

1. 折扣顺序固定：店铺折扣 → 平台券 → 跨店补贴。
2. 每步只以适用行“尚未优惠的正金额”为权重分摊，余分按 `line_id` 字典序。
3. 跨店补贴以适用行**优惠前金额**判断 `threshold`；不足则购买时点即全额
   失效，不计提出资。
4. 出资归属：`merchant_share` 是商家承担的**绝对比例**（如 0.3/0.2 表示商家
   合计承担 50%），平台承担余量（剩余 50%）；平台券 `merchant_share={}`
   即平台全担。未参与某优惠的商家（如 m2）不为该优惠出资。

### 退货与失效

* `return_qty` 为累计退回，取消与退货都减少留存量；`goodwill` 是商家额外
  现金补偿，与折扣、退款抵减分开。
* 退货先重判跨店门槛：留存适用金额不足 `threshold` 时，该补贴**全额失效**，
  其金额整体走失效冲回，不再按件回冲，避免同一金额扣两次。
* 仍有效折扣按件回冲（行折扣按件拆分，余分字典序）。
* 冲回按各出资方“尚未冲回的净余额”分摊，保证任一方累计冲回不超过原出资。
* 商品应退只扣事件后仍有效的折扣；补贴失效收回的消费者已享补贴为“消费者
  应补”，先抵减本次应退，**最低退款为零**，抵不掉的部分单列**待追收**
  （应收，不是已收），按失效补贴原归属挂账。

### 守恒与非负守卫

每个篮子核定后强制校验：

* 消费者支付 + 购买时点折扣 = 优惠前总额；
* 商家出资 + 平台出资 = 购买时点折扣；
* 应补 = 抵减 + 待追收；退款 = 应退 − 抵减；
* 商家+平台冲回 = 各行冲回落点；冲回不超过原出资；
* 单位成本非负、留存数量非负。

任一不成立即抛错，不产出看似平衡但归属错误的结果。

## 费用确认与争议

* `confirmed_funding` 按 (basket, merchant, discount) 界定范围；引擎重算值
  与已确认值之差显式记为 `confirmation_delta`，状态为
  `delta-pending-confirmation`，等待对方确认，历史确认不被覆盖。
* 未决异议只冻结其影响范围：`unit_cost` 冻结该商家本篮费用键；`return_qty`
  改变全篮冲回基数，冻结篮内全部参与商家；其余篮子与费用照常核定。
* 异议成立后整篮重算，关联商家的分摊基数与活动利润同步变化，而非只改一行。

## 收益识别的边界

* 人群在活动前确定；`web` 渠道只有参加者、没有同期未参加对照，因此 web
  参加者的个体因果效应**不可识别**，单列保留，不进 ATE。
* 可比支持只在 `app` 渠道内、按 `category` 分层、以 `tenure_days` 与
  `pre_period_spend` 近邻匹配建立；共同支持外的参加者不计入因果估计。
* 报告同时给出朴素对比（暴露选择偏差）与匹配 ATE 及自助法 95% 区间；
  含零购买账户，未成熟篮子标注/剔除。
* 本次退款率仅在本次门槛与力度下观测，不得外推为任意优惠力度下的不变规律。

## 预算与方案

* 可用预算 = 现金 − 争议预留（`budgets.disputed`）− 已接受方案占用。
* 方案独立可行性对当前可用余额判断；多方案同时接受时返回**实际缺口**，
  不允许两份单独可行的方案一起超支。
* 只有门槛、品类在历史中出现过的部分才标记“有历史支持”；无支持的门槛
  不做确定收益推断。所有资金为内部预算，不接真实支付。

## 溯源

`trace` 输出把一笔核定连到：原篮子事实及来源包、商品行、折扣合同、截点
可知的退货与异议事实、已确认出资，以及核定本身。两个核定版本可 `diff`，
直接看到后补售后改变了哪些退款、平台净支出、商家利润与待追收。
